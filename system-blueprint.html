ChatBranch 聊天文件分支系统 （命名提案，可随时改：备选「千层楼 QianCeng」「FloorFS」）

一套跑在标准 ST 聊天文件之上的分支系统：以「楼层 / Swipe 组 / 分支 / 聊天家族」重新组织聊天数据， 分支只存增量、永不整文件复制；前端扩展独立可用（可视化 + 增量分支 + 零网络秒切分支）， 后端插件为可选增强（全局关系扫描 / 增量导出 / 注入迁移，全部用户可配）。 文件格式 100% ST 标准，vanilla 环境优雅降级。零核心修改，不拦截 fetch。

✓ 前端扩展：必需、独立可用 ✓ 后端插件：可选增强 ✓ 标准 JSONL 兼容 ✓ 零核心修改 ✓ 不拦截 fetch 第一期不解决：ST 全量加载瓶颈 接管聊天文件系统 = 数据组织层，非新格式

①一句话本质

它是什么

聊天数据的组织层：楼层数据本身就是标准 ST 聊天文件的一部分（metadata 开放字典 + 消息行），不发明第二种格式，不需要独立数据库。

它解决什么

  • 原生分支 = 整文件复制 → 改为增量引用（共享前缀只存一份）
  • st-timelines 全量加载看关系 → 后端只扫每个文件第一行 header 建全局关系图
  • 切换分支 = 换文件 → 改为前端内存折叠/展开，零网络请求
  • 无可视化 → 分支树 + 分支视图 + 分叉点标记

为什么能保证标准

ST 的 chat_metadata 与消息 extra 是开放字典，未知 key 全程原样读写（ST 自家扩展即此机制）。分支树全部数据住在 chat_metadata.extensions.branches，主线性数组永远是合法消息行——vanilla ST 打开看到默认分支，其余数据原封不动。

前端 only 为什么够

分支切换、分叉、swipe、编辑全部是同一份内存数据的重排；保存走 ST 原生路径（FS/SQLite/MySQL/PG 四种模式自动兼容）。后端插件只做跨文件的事：扫描、导出、注入、迁移。

核心概念（分支系统）

楼层 Floor

一条消息位，家族内全局编号。主线性数组的一行 ↔ 活跃分支的一个楼层。

Swipe 组

一个楼层的一组消息变体。多变体时映射为该行的 ST 原生 swipes[]。

分叉点 Fork

同楼层存在 >1 个 Swipe 组的楼层。树/分支视图中标记 ⎇。

分支 Branch

从分叉点之后的一条 Swipe 组路径引用（非复制）。分叉楼层本身共享，分叉后的新楼层归属新分支。

聊天家族

互为分支的聊天集合 = 一个文件。新建聊天自动建家族，可编辑名称。

编辑共享楼层

第一期：全局可见（同一行，改了都看到）。Merge 第一期不做。

④存储设计 · 文件解剖

    


// chat1.jsonl —— 100% 标准 ST JSONL，每行含义：
{"user_name":"unused","character_name":"unused",
 "chat_metadata":{ ..., "extensions":{ "branches": {...} } }}   ← 第 1 行：分支树住这里（开放字典）
{"name":"我","is_user":true,"mes":"...","send_date":1771009329448,...}          ← 活跃分支 楼层1
{"name":"Seraphina","is_user":false,"mes":"...","swipes":["...","..."],"swipe_id":1,...} ← 楼层2（多变体=ST 原生 swipe）
...                                                                    ← 活跃分支的楼层线性序列

// branches 内部（示意）：
{ "version": 1,
  "active_branch": "main",
  "branches": [
    { "id":"main",  "name":"主分支", "is_default":true },
    { "id":"b2",    "name":"支线",  "fork_base": 4,  // 第4层后分叉 → 楼层1-4共享，第5层起私有
      "path": {"5":"g-b2-5", "6":"g-b2-6"} }  // 分支路径 = 楼层→Swipe组 的引用
  ],
  "groups": { "g-b2-5": {"floor":5, "variants":[{"name":"Seraphina","mes":"..."}], "active":0} }
              // ↑ 非活跃分支的增量消息住这里；活跃分支的组就在主线性数组里，不重复存
}

    

    
格式契约（以原生格式为唯一权威）

    

      
权威依据
research/01-jsonl-format-and-serialization.md：header 元数据嵌套在 chat_metadata；消息正文字段是 mes；send_date 毫秒；integrity 乐观锁基于整文档。

      
验收标准
Round-trip：原生 JSONL → 插件操作 → 落盘 → vanilla ST 可读、默认分支无损；增量导出文件与手工整理的标准文件 diff 无异常。

      
已废止的自创格式
此前实现的 content/role 字段、秒级时间戳、平铺 header、独立 SQLite 事实源 —— 全部废止（见决策日志）。

    

  


  
  

    
⑤决策日志 2026-08-29 grill 对齐

    

      
决策点结论

      
系统根本定位接管聊天文件系统：分支成为聊天数据的组织方式已定

      
交付形态前端扩展（必需、独立可用）+ 后端插件（可选增强）。零核心修改是硬约束——调研报告「改 chat-repo.js」路线废弃已定

      
事实源标准 ST 聊天文件本身；分支数据装进文件第 1 行 chat_metadata.extensions.branches（单文件自包含：拷走/分享/迁移分支自动跟走，vanilla ST 可开，四种存储模式兼容）已定

      
fetch 拦截不做。本架构在 ST 原生数据流内工作，无需改道（04 调研文档「事件同步」建议正是上一版跑偏的根源，废止）已定

      
接管范围按聊天家族 opt-in：未接管聊天 100% 原生；新聊天/导入自动进家族。关插件 = 完全原生，无残留已定

      
保险丝（镜像写回）由「增量导出」承担：手动/自动导出、注入均用户可配。默认形态与写回策略在待确认清单细化中

      
格式契约以原生格式为唯一权威（mes / chat_metadata 嵌套 / 毫秒 / integrity）+ round-trip 验收已定

      
分支语义分叉楼层本身共享，分叉后新楼层归属新分支；建分支禁止复制消息（旧实现废止）已定

      
编辑共享楼层第一期全局可见；Merge 不做；单人聊天沿用 PRD

      
原生书签/检查点收编式：不阻断原生流程，监听 CHAT_BRANCH_CREATED，检测到接管家族上产生整文件复制时弹窗询问「收编为楼层分支？」（收编=转引用+删复制文件，默认不收编）已定

      
旧代码处置后端路由骨架可改造为「可选增强」（扫描/导出/注入）；独立 SQLite 事实源与自创格式部分重写；前端树 UI 思路保留、数据源重写待执行

      
第一期验收线（v1）单文件全旅程（纯前端）：ST 正常聊天 → 任意层分叉 → 双分支各自续聊 → 零网络切换 → 关插件 vanilla ST 验证默认分支无损 → 增量导出可导入原生。后端插件 v1 不参与已定

      
增量导出可配置：关 / 仅手动 / 每次保存后自动，默认「仅手动」（面板按钮始终可用）。导出物 = 无 branches 的纯标准 JSONL已定

      
写入路径（吃 Luker 的 patch）继续聊天 → 原生 append（沿用双去重）；结构操作（分叉/折叠/展开/分支增删改名/编辑折叠消息）→ /api/chats/patch：operations 打在 body、chat_metadata 字段携带新 branches、integrity 乐观锁 + 409 冲突重拉重放；大改回退 save。全程核心已有端点，零修改已定

      
教训存档① 约束冲突（改核心 vs 插件）未裁决 → 集成被无限后推 ② 存储方案四换未清理残留约束 ③ 先做好做的 UI、地基后置 ④ 格式正向发明而非逆向映射。完整审计见 research/10-design-drift-audit.md勿重蹈

    

  


  
  

    
⑥边界与已知代价

    

      
明确不做（第一期）
  • 不修改 Luker 核心、不拦截 fetch
  • 不做 merge、不做群聊
  • 不解决 ST「整文档加载」的全量读取瓶颈（真分页需改 repo 层，已排除；未来如解禁可叠加）

      
接受的代价
  • 大聊天打开速度 = ST 原生水平（瓶颈不变）
  • 分支极多时 header 增大（总量仍严格优于原生整文件复制）
  • vanilla ST 下只能看到默认分支（数据不丢，功能降级）

      
原生书签/检查点
已定「收编式」：不阻断原生流程；检测到接管家族上产生整文件复制时弹窗询问是否收编为楼层分支（默认不收编）。见演示①的 🔖 按钮。

      
并发与一致性
分支树随整文档走 ST 原生 integrity 乐观锁；前端扩展内的折叠/展开在保存前完成，保持「文档自洽」。

ChatFilesys 聊天文件系统 · 纯数据库模式

接管酒馆聊天文件系统：单个数据结构内的楼层级分支（分支只存增量、永不复制文件）+ 纯数据库存储（楼层分片入库，jsonl 仅导出时存在）+ 生态无感（fetch 拦截伪装成 jsonl，渲染与其他插件全部照常）。 安装后提示「录入数据库并智能合并 → 删 jsonl（默认删）」，之后大聊天按楼层分片毫秒级加载。

①一句话本质

它是什么

聊天文件系统的重组织：真分支住进单个数据结构（楼层/Swipe组/分支路径），消息住进数据库分片。不再是「一堆互相复制的 jsonl 文件」。

它解决什么

  • 原生分支=整文件复制 → 增量路径引用（共享前缀只存一份）
  • 超大 jsonl 打开慢 → 楼层分片按需读（不再整文件 JSON.parse）
  • 文件间重复历史 → 指纹合并去重（完全相同去重、LCP 对齐分叉）
  • 切换分支=换文件 → 内存重投影 + 整枝联动（零网络切换）

swipe 与 branch 正交（N8）

swipe 组可有数量上限（按性能定）的变体；swipe 不影响剧情叙事，只有 branch 是真分支。外部插件改了 swipe → 按内容候选吸收，不产生分支。

生态为什么无感

宿主与其他插件都经 fetch → /api/chats/* 读写聊天。接缝层拦截这些请求：读=从库分片拼装合规响应，写=解包转写库。渲染管线零变化。

关键事实（仓库证据）

Luker 已有 ChatRepo 四引擎

服务端 FS/SQLite/MySQL/PG 抽象已存在，但插件零核心修改下无法注入新引擎——接缝只能做在前端 fetch 层。

原生 DB 引擎≠性能收益

Luker 原生 SQLite 引擎按整文档存（chats.doc 单列 blob），不解决「超大聊天加载慢」——分片 schema 必须由本插件自建（design.md §2）。

fetch 拦截有宿主先例

Luker 自身 ws-delivery.js installFetchProxy（含 disposer）、frontend-log-manager.js 就在 patch 全局 fetch——技术路线宿主自己背书。

纯前端不绑 Authority

聊天数据本可经官方 /api/chats/* 读写；Authority SQL 只是档1 候选（N3/N9：实测瓶颈则弃用）。

③数据模型与存储

// 概念（N4 同构认定：愿景「分支分组+绑定」≡ 此模型）
家族 Family    = 互为分支的聊天集合（取代「聊天文件」；zip 只是导出容器）
楼层 Floor     = 一条消息位，家族内全局编号
Swipe 组 Group = 楼层内变体集合（变体数上限按性能定，N8）
分支 Branch    = 从分叉点起的组路径引用（唯一真分支语义）

// Authority SQL 档表设计（design.md §2）
families(id, character_id, name, ...)          ← 解绑/重绑=改一列（N16）
floors(family_id, floor_no, variant_id, content, content_hash, ...)
branches(family_id, branch_id, parent_branch_id, name, fork_floor, ...)
branch_paths(family_id, branch_id, floor_no, variant_id)
↑ 楼层分片=按需读的直接来源；content_hash=智能合并物理基础；
  parent_branch_id 允 NULL=图结构预留（远期 merge/DAG 不锁死）

导出（N2：jsonl 仅导出时存在）

branch 导出

按 branch_paths 取楼层行 → 拼标准 jsonl（单文件，vanilla ST 可直接打开）。

家族导出

遍历 branches → 每 branch 一份 jsonl → 打成 zip 包。家族是数据概念，zip 只是导出容器，二者不得混写。

jsonl 映射模式（功能1）

可选的双写绑定形态：开启后库↔jsonl 同步（用即生成、原样保存），供网盘同步/直读磁盘的场景。

④导入与智能合并

安装旅程（N2）

  • 安装 → 检测存量 jsonl（原生聊天 + chatfilesys 存量）
  • 提示「录入数据库并智能合并」
  • 提示「是否删除 jsonl」——默认删（回收站 N15）
  • 「保持 jsonl 双写绑定」——默认否

智能合并（N10）

  • 完全相同楼层（content_hash 相同）→ 幂等去重
  • 前缀相同 → 最长公共前缀（LCP）对齐为分叉点，剩余各挂子分支
  • hash 冲突时 send_date+发送者第二重校验
  • AI 语义合并（LLM 判同剧情点）不进 MVP

回收站（N15）

  • jsonl 移入插件管理的服务端回收站目录（Authority fs）
  • 保留 N 天（默认 7）后自动清理，期间可一键还原
  • 删除动作本身仍需确认弹窗（用户数据属 PARDON 范围）

跨聊天同层合并（N16/功能3）

同角色卡不同 jsonl → 同一套指纹对齐算法 → 合并为同层多分支。文件间重复历史由此消灭。

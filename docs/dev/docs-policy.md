# 文档政策（真源分工与防漂移）

## 它做什么

规定**同一件事的细节只允许在一处写**，另一处只指路、不复制。

这不是洁癖：两处都写细节，早晚会一处更新、一处没更新，读者不知道该信哪个——
更糟的是，**对不上时没人知道以哪个为准**。

## 怎么用

### 分工表

| | `docs/`（本站） | `.trellis/spec`（本机） |
| --- | --- | --- |
| 受众 | **人**：使用者、贡献者、想评估这个项目的人 | **agent**：写代码时要遵守的细则、落点、禁令 |
| 是否发布 | **是**（GitHub Pages） | **否**（被 `.gitignore` 排除，只在开发者本机） |
| 内容形态 | 功能怎么用、边界、架构说明、开发流程 | 编码约定、命名与禁令清单、逐文件落点、file:line 证据 |
| 语气 | 解释「为什么」 | 命令「必须/禁止」 |

### 判定方法（怎么知道已经漂移了）

> **若两处都在叙述同一件事的细节 → 已经有漂移风险，必须改成一处叙述、另一处指路。**

分界大致落在「粒度」上。以目录结构为例：

- 本站的[架构](/dev/architecture)页写**层次与不变式**（哪层放什么、依赖方向、为什么这样切）——
  这是人理解项目要的粒度，变化慢。
- `.trellis/spec` 里的对应文件写**逐文件清单、命名前缀、禁止 import 的清单**——
  这是 agent 动手时要的粒度，随代码走。

两边都写「目录树」这件事，但**粗一档的留在本站，细一档的留在 spec**，且本站**不复制**细的那份。

### 一条本仓必须写明的事实

**`.trellis/` 被 `.gitignore` 排除**，所以：

- 里面的规范与任务文档**只存在于开发者本机**；
- 引用它们时**不得写成「已发布」**；
- **不要从本站链接过去**——对读者那是**死链**（这条不是假想的风险：本仓群真出过一次「资料索引指向
  一个不存在的目录」，agent 按索引去读、读不到、也不报错，静默按「没有资料」继续干）。

### 新增页面时的两条登记

1. **用户能用的功能** → 回登记到[指南总览](/guide/)那张「功能一览」表（一行 + 一句话）。
   表是给读者的地图，也是核对的基准。
2. **未做到的事** → 不单独开页（会让人以为它可用），统一进[路线图](/dev/roadmap)与
   [边界与未做到（汇总）](/guide/boundaries)。

> **一条有意例外**：[隐私边界](/guide/privacy)讲的**现在还没有**的东西也必须开页。
> 理由：用户要拿「能保护什么、不能保护什么」做部署决策，藏起来才是误导。

### 计划放在哪

**路线图只在[路线图](/dev/roadmap)页写全**。仓库 `README.md` 只留一句指路，
不维护第二份进度清单——两份清单是本仓已经真实踩过的坑（同一件事在两个月里对不上三次）。

## 边界与未做到

- **本政策靠纪律执行，没有自动检查**：没有脚本会在你新增页面时拦住你。
  能做的是**构建期**的检查——站内死链会让构建报出来，但「该登记却没登记」不会。
- **机向规范不随仓库分发**：`.trellis/` 不进版本库，所以外部贡献者看不到那份细则。
  这是成本，换来的是「本机工作记录不必脱敏、也不必担心误发布」。
- **本站不建多语**（结构预留，未实现）。

## 失败与降级时的表现

- **两处细节打架**：以**人向**为准还是以 spec 为准，本政策不预设——判据是**哪一处是这件事的权威**。
  功能行为、边界、计划的权威在本站；编码约定、落点、禁令的权威在 spec。
- **发现漂移**：把其中一处改成「指路」，不要在两处各改一半。
- **历史事故留档**：本仓曾有一轮术语替换脚本把**记录该替换事故的句子自己**也改坏了，
  导致一句自相矛盾的话留了下来。处置是**更正 + 留一句注记说明原因**，不静默抹掉
  （见[路线图](/dev/roadmap)末尾的更正说明）。

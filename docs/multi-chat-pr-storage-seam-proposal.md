# Luker 多聊天加载 PR · 存储接缝建议书

> 用途：为「允许多聊天同时加载、并发读写互不干扰」的 Luker 上游 PR 提供存储接缝设计建议。
> 立场（任务 09-24-realign-pure-db 裁定 N1）：**插件只要求「允许多并发场景」，不耦合、不限定 PR 形态**。本文档是建议而非依赖——PR 采纳与否、形态如何，不影响插件的接缝路线（fetch 拦截，N6）。
> 日期：2026-09-24。

## 一、为什么多聊天加载天然需要一个存储接缝

「同时加载多聊天」一旦成立，以下旧假设全部失效：

| 旧假设 | 多聊天下的失效方式 |
|--------|-------------------|
| 「当前聊天」是全局单例（内存一个 chat 数组） | 变成 N 个并发聊天上下文，每个有自己的 header/消息体/integrity |
| 保存=对当前单例的全量落盘 | 变成按聊天隔离的并发写，写写冲突需要按聊天粒度的锁 |
| 加载=一次拉一个文件 | 变成批量/选择性加载，需要按需分页的读取语义 |

这三条恰恰是**存储层**的职责——所以多聊天 PR 天然触及存储边界。在 PR 里顺手把边界定义清楚，比让每个前端插件各自 monkey-patch fetch 要干净得多。

## 二、接缝的三种定义方式（建议 PR 采用 A，附 B/C 供讨论）

### 方案 A：加载/保存生命周期钩子（推荐）

Luker 核心在聊天的加载与持久化路径上暴露官方钩子，钩子签名面向「聊天数据供应商」：

```js
// 概念示意，具体命名以上游评审为准
registerChatStorageProvider({
  id: 'chatfilesys',

  // 加载：核心要某聊天时，先问已注册供应商
  async loadChat({ avatarUrl, fileName }) {
    // 返回 [header, ...messages]（与 /api/chats/get 响应同构）
    // 返回 null = 不由本供应商负责，核心走默认存储
    return null;
  },

  // 保存：核心持久化时通知供应商
  async persistChat({ avatarUrl, fileName, doc, integrity }) {
    // 返回 { ok, integrity } 或 null（不接管）
    return null;
  },

  // 列表可见性（可选）：聊天选择器里显示什么
  async listChats({ avatarUrl }) { /* 返回 null = 默认 */ },
});
```

要点：
- **返回 null 即放行默认路径**——供应商机制天然可选，vanilla 行为零变化，PR 审核阻力最小。
- 钩子面向「聊天文档」级别（header+消息数组），不暴露存储内部结构（引擎仍是 ChatRepo 的私事）。
- integrity 乐观锁语义沿用：persistChat 返回新 integrity，冲突返回 409 语义由核心与供应商协商。
- 与 ChatRepo 四引擎抽象的关系：钩子在**端点层之下、引擎层之上**——供应商相当于第五种「虚拟引擎」，但注册在前端进程内，不改服务端引擎注册表（保持零服务端侵入）。

### 方案 B：分页读取语义（强烈建议顺带定义）

多聊天加载与「超大聊天按需读」是同一个诉求的两面。建议 PR 顺带把读取语义从「整文档」升级为「可分页」：

```
GET /api/chats/get        → 现状：整文档（保留，向后兼容）
POST /api/chats/page      → 新增：{ avatar_url, file_name, from_floor, limit }
                             → { header, floors: [...], has_more, integrity }
```

核心前端可先仍整读（渐进迁移），第三方（含本插件）立即可用分页读。这个端点本身不依赖多聊天合并，可拆成独立小 PR 提前落地。

### 方案 C：仅并发语义（最小 PR）

只定义多聊天上下文的生命周期与并发规则（互不干扰、按聊天粒度锁/integrity），存储接缝完全不碰。PR 最小、最易合并，但超大聊天分片存储仍需前端各自 hack（本插件退回 fetch 拦截路线）。

## 三、并发语义建议（无论选哪个方案都适用）

1. **按聊天粒度隔离**：integrity/写锁/事件以 (avatarUrl, fileName) 为单位，不做全局聊天锁——多聊天并发写的正确性边界。
2. **读不阻塞写**：读方拿快照（integrity 标记），写方提交时校验——现有乐观锁的自然延伸。
3. **多聊天事件携带聊天标识**：`CHAT_CHANGED` 类事件需带 chatKey，前端按 key 路由到对应上下文——多页签/多聊天 UI 的同步基础。
4. **内存上下文生命周期归核心管**：卸载某聊天=释放其上下文并退订其事件，防止多聊天下监听器泄漏。

## 四、与本插件的关系声明

- 本插件（ChatFilesys）纯库模式的接缝路线已定为 **fetch/API 拦截**（裁定 N6），不依赖本建议书被采纳。
- 若上游采纳方案 A/B，本插件可切换到官方接缝（保留 fetch 拦截作为未升级宿主的回退），伪装层代码量显著减少。
- 本建议书独立于插件代码演进，可单独提交上游讨论。

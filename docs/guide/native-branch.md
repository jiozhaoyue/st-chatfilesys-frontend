# 原生「创建分支 / 创建检查点」接管

## 它做什么

让宿主的**原生按钮**在纯库/双写模式下**不落复制文件**，而是直接在库内成一条分支。

**问题背景**：宿主点原生「创建分支」时会**先落一个复制文件**（把整份聊天另存到一个新键），
分支关系只存在于那个文件里。纯库模式不要文件、要库内分支，所以必须在写路径上认出
「这次写的是某个已是家族聊天的新分支/检查点」，并把落点改成库内一条新分支。

## 怎么用

用法完全不变——**照旧点宿主原生的「创建分支 / 创建检查点」按钮**。

**插件不做任何"新建分支"的按钮**：新增分支只走宿主原生入口。
你不需要学一套新的操作方式，接管发生在看不见的地方。

## 插件怎么识别这次写是「分支/检查点」

三个判据（都有真机取证）：

1. **父线索**：宿主写新键时，正文首行 header 里的 `chat_metadata.main_chat` 等于当前聊天键。
   这是**权威**判据。
2. **内容必须是父分支当前投影的逐行前缀**——这是一道**保守闸门**：
   宁可**透传**（放给宿主原样处理）也不误吞。
3. **类型判定**：分支名由宿主自动生成、**用户不可改**（形如 `X - Branch #<n>`）；
   检查点名**用户可改**（弹窗留空才是 `X - Checkpoint #<n>`）
   → 命中分支样式即为分支，其余即为检查点。

## 边界与未做到

- ⚠️ **装了消息改写类插件时，接管可能不触发。** 当前内容闸门是**整行 JSON 全等**比对，
  而宿主与变量类插件会在「载入 → 写出」之间给消息对象加字段
  → 两侧序列化不同 → 闸门不通过 → **接管不生效**（这是真机实测结论，不是推测）。
  闸门放宽是已知待办（见[路线图](/dev/roadmap)）。
- **不触发时不会丢数据**：整条路径**透传**给宿主，走它原本的落文件行为——
  你得到的是一个原生复制文件，而不是一条库内分支。
- 只有**分支/检查点**这两条路径会写 `main_chat`，所以「非分支样式 ⇒ 检查点」不会误判其他功能。

## 失败与降级时的表现

- **判据不满足 → 静默透传**（这是**正确行为**，不是失败）：宿主按原样处理，
  用户拿到的仍是可用的原生结果。
- 接管成功时走的是与[导入](/guide/import)同源的合并逻辑（指纹对齐），
  **不复制正文**——共享部分在库里只有一份。

# 装了别的插件会不会坏

本插件改的是「聊天内容存在哪里」。你装的其他插件如果也在读写聊天，就可能受影响。
这一页把「哪些会受影响、影响成什么样、怎么办」说清楚。

先说结论：**大多数插件不受影响**。受影响的是**需要翻聊天文件列表**的那一类。

## 怎么判断某个插件会不会受影响

问它一个问题就够了：**它从哪儿拿聊天数据？**

### 一、它用酒馆自己的收发消息功能

**不受影响。** 这类插件（自动记笔记、改消息显示、加按钮之类）做的事最终都会经过酒馆自己的
存读通道，而本插件正是在那条通道上工作的。它写的内容照样进库、照样能切分支。

### 二、它直接改当前聊天在内存里的内容

**不受影响。** 内存里的聊天和库里的内容是同一份东西的两面；它改完，酒馆保存时本插件会接住。

唯一要留神的是：它会不会也往聊天头里写一个叫 `chatfilesys` 的字段。
本插件只用聊天头里的两项（自己的模型、家族版本号），其余一字不改。
真要撞名了，那是**改名的活**，不能靠「谁写得晚谁赢」。

### 三、它要「列出这个角色有哪些聊天」

**这一类曾经会坏，现在已修好**（2026-09-28）。

在纯库模式下，聊天内容只在数据库里，磁盘上那份聊天文件已经移进了回收站。
从前这类插件去问酒馆「有哪些聊天」时，**会得到「一个都没有」**——它不会报错，
只是列表空空，或者告诉你「找不到聊天」。

现在的做法是：酒馆被问到「有哪些聊天」时，本插件会把**数据库里的聊天补进那份列表**
（磁盘上有的照旧保留，只追加）。所以这类插件现在能正常看到。

设置里有一项「让『列出聊天』也看得到库里的聊天」可以关掉——关掉就回到只列磁盘文件。

**一处如实的说明**：补进去的那些条目**没有「多少条消息」和「最后活动时间」**。
要拿到它们得把每个聊天的内容都读一遍，代价随聊天数线性增长，所以没有做。
列表里这两栏会是空的——**空着而不是显示 0**，因为「0 条」与「不知道」是两回事。
需要看内容时点进去即可（读内容那条路是通的）。

### 四、它把数据存在自己的地方

**不受影响。** 它的数据和聊天文件本来就没关系。

## 现在能怎么办

- **一般不需要做什么**——上面四类里，只有第三类曾经需要留意，而它已经修好了。
- 仍然建议：**需要和别的插件打配合的那几个聊天，留在文件态**（不转库）。
  这是最稳的做法，因为别的插件不需要理解「库」这个概念。
- 双写模式（库里一份 + 磁盘上一份）介于两者之间：既拿到本插件的分支能力，
  磁盘上也一直有文件。代价是多占一份磁盘空间。

## 已知的限制

- **补进列表的条目没有「消息条数」与「最后活动时间」**（理由见上面第三类）。
- 个别插件可能走别的端点或直接读磁盘路径而不是问酒馆——那类插件**不在能帮到的范围内**。
  遇到时把它记下来（`tests/e2e/plugin_compat_scan.py` 可以帮你分类），
  再决定是让它改成问酒馆、还是那个聊天干脆留在文件态。

# 装了别的插件会不会坏

本插件改的是「聊天内容存在哪里」。你装的其他插件如果也在读写聊天，就可能受影响。
这一页把「哪些会受影响、影响成什么样、怎么办」说清楚。

先说结论：**大多数插件不受影响**。受影响的是**需要翻聊天文件列表**的那一类。

## 怎么判断某个插件会不会受影响

问它一个问题就够了：**它从哪儿拿聊天数据？**

### 一、它用酒馆自己的收发消息功能

**不受影响。** 这类插件（自动记笔记、改消息显示、加按钮之类）做的事最终都会经过酒馆自己的
存读通道，而本插件正是在那条通道上工作的。它写的内容照样进库、照样能切分支。

### 二、它直接改当前聊天在内存里的内容

**不受影响。** 内存里的聊天和库里的内容是同一份东西的两面；它改完，酒馆保存时本插件会接住。

唯一要留神的是：它会不会也往聊天头里写一个叫 `chatfilesys` 的字段。
本插件只用聊天头里的两项（自己的模型、家族版本号），其余一字不改。
真要撞名了，那是**改名的活**，不能靠「谁写得晚谁赢」。

### 三、它要「列出这个角色有哪些聊天」

**这类会受影响，而且症状很隐蔽。**

在纯库模式下，聊天内容只在数据库里，磁盘上那份聊天文件已经移进了回收站。
于是这类插件去问酒馆「有哪些聊天」时，**会得到「一个都没有」**——它不会报错，
只是列表空空，或者告诉你「找不到聊天」。

**怎么确认你遇到的是这个**：本插件的管理弹窗里，「角色卡的聊天」页签**列得出来**
（它自己会把磁盘上的和库里的合起来数）。同一时刻那个插件列不出来，就是这个问题。

受影响的常见类型：聊天备份、聊天仓库、聊天合并、聊天索引、按聊天统计的工具。

### 四、它把数据存在自己的地方

**不受影响。** 它的数据和聊天文件本来就没关系。

## 现在能怎么办

- **改用双写模式**：库里存一份，同时保留一份标准聊天文件。磁盘上一直有文件，
  依赖文件列表的插件就能正常工作。代价是多占一份磁盘空间、多一次写盘。
- **只对少数聊天用纯库模式**：把不折腾插件的那些聊天转进库，需要和别的插件配合的留在文件态。
- 日常备份与合并这类操作，也可以直接用本插件自带的导出与「角色卡的聊天」页签。

## 已知未解决

「列表里看不到纯库模式的聊天」这件事，目前**没有做到让别的插件也看得见**。
要让它正常，本插件需要在酒馆的「列出聊天」通道上也接一手、把库里的内容一并报出去。
这件事要不要做、怎么做，写在[路线图](/dev/roadmap)里，尚未实施。

在此之前，如果你的用法离不开某个「列聊天」类的插件，**请用双写模式**。

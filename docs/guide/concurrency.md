# 并发写与冲突

## 它做什么

**两处以上同时改同一个聊天**时，保证不会**静默互相覆盖**，而是明确报冲突。

## 怎么用

你不需要做任何事。冲突发生时，行为是**明确回冲突**，然后**酒馆按它自己的规矩重拉重写**——
也就是你在原生酒馆里早就在经历的那套流程，本插件没有另发明一套。

## 机制

「库」带一个**家族级字符串版本号**，每次成功写生成一个新值。写入时：

| 情形 | 行为 |
| --- | --- |
| 入向版本号与库内值**字符串相等** | 允许写 |
| **不相等** | 返回**冲突** → 接缝映射为 `409` → 酒馆重拉重写 |
| 调用方**没带**版本号 | 不锁（例如宿主原生保存不带版本号，或显式强制覆盖） |
| 库内为空（家族还没写过） | 放行**首次写** |

### 为什么必须是字符串（一个被修掉的真实缺陷）

版本号**曾经是数字**。数字形态迫使接缝做「本插件形态 ⇄ 数字」的双向桥接，
而桥接对**不是本插件形态的 uuid**（宿主自己的 integrity）**只能放行、不能锁**
→ 结果就是**两处同时改同一家族时静默覆盖**。

改成字符串之后：**不再桥接、不再放行**——入向值必须与库内值字符串相等才允许写。
而宿主的 `chat_metadata.integrity` 本来就是字符串，所以两者**形态统一**，不必再转换。

## 边界与未做到

- 这道保护覆盖**家族级写入**。宿主对聊天文档自身的并发由**宿主自己**负责，
  本插件不越权代管。
- **多插件共存实测尚未完成**（见[路线图](/dev/roadmap)）——
  即"多个插件同时在场时这套冲突判定是否仍然成立"，目前只有单插件在场时的真机结论。
- 冲突**不是错误**：它是正常语义，表示"你手上的那份已经旧了"。

## 失败与降级时的表现

- 冲突时**不重试、不合并**：如实交回宿主，由它重拉重写——避免插件自作聪明地覆盖别人。
- 其它写入失败按原因区分：内容与宿主假设不符 → `409`；其余 → 400 级，宿主自行回退全量保存。

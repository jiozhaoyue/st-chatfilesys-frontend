# 隐私边界（如实）

> **本页只讲边界，不讲承诺。** 它存在的理由是：**能保护什么、不能保护什么**，是你决定怎么部署的依据。
> 把做不到的部分藏起来，比不写更糟。

## 现状：今天到底保护了什么

| 层 | 今天的状态 |
| --- | --- |
| 库内数据 | **未加密**。家族模型与消息正文以明文存在所选后端（服务端库 / 官方通道容器 / 浏览器 IndexedDB） |
| 磁盘聊天文件 | **明文**。JSONL 增强与双写模式下，磁盘上就是标准聊天文件——宿主自己要读它才能渲染聊天 |
| 库内加密 / 纯库加密 | **尚未实现**（在规划中，见[路线图](/dev/roadmap)） |

**结论**：**今天不要把它当成隐私保护手段。** 它能保护的是「聊天记录不因分支操作被复制成多份文件」，
**不是**「别人读不到你的聊天」。

## 能做到的保护（规划中的目标，尚未交付）

目标形态是：**归档保密** —— 历史归档在**客户端**加密后落库，服务端只存密文；
只在**纯库模式**下生效（因为只有该模式不落明文 jsonl）。

配套设计（尚未实现）：
- **分列加密**：消息正文加密；**层号 / 分支 / 时间 / 指纹等结构字段保持明文**，
  这样分支、楼层、图这类查询与排序不受影响，牺牲的只是**正文检索**。
- **无感密钥**：密钥由登录口令派生（不要求用户手工保管密钥）；解密在客户端进行。
- **如实声明**：只承诺**静态层**（防拷库、防备份泄漏、防跨用户）。

## 做不到的部分（**这三条不会因为努力而消失**）

1. **运行期的明文仍有几条必经之路。**
   酒馆的默认形态是「浏览器组好提示词 → 发给宿主服务器 → 服务器代发给模型」。
   **服务器在这一步能看见全部聊天明文**——包括你的归档在**被继续对话**时的那一段。
   要连这一步都绕开，需要浏览器直连模型等条件，属另一套部署形态。
2. **恶意管理员原理上防不住。**
   **浏览器里跑的 JS 是服务器发过来的**——改一版页面即可把密钥取走。
   这不是实现缺陷，是「网页应用」这个形态的边界。
3. **删除与篡改永远拦不住。**
   磁盘与服务都在管理员手里。加密能争取的只有**机密性**；
   **完整性与可用性（删库、停服）始终在管理员手里**。

## 一条必须记住的取舍

**「只有你能解密」与「丢了能恢复」本质互斥。**
密钥一旦丢失（口令忘记、浏览器数据被清），加密后的历史**永久不可解**——
这是数学性质，不是本插件的缺陷。任何声称两者兼得的方案都在骗人。

## 失败与降级时的表现

- 加密不可用（如后端不支持、密钥不可得）时，**不得静默降级为「明文落库」**——
  必须**明确告知**，让人知道当前没有保护。
- 这条纪律与「后端不可用不阻断使用」并不冲突：**功能可以降级，保护不能假装。**

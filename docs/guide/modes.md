# 三种模式

## 它做什么

决定**聊天内容主要存在哪里**。这是本插件最根本的一个开关，在**弹窗的「设置」页签**里三选一。

## 怎么用

### 先认识四个概念

| 概念 | 一句话 |
| --- | --- |
| **聊天家族** | 一个角色名下互为分支的一批聊天，合成一个家族。从前它们是磁盘上互不相干的一堆文件；现在是同一家族里的不同分支。 |
| **楼层** | 一条消息占一个楼层位，家族内**统一编号**。不管走哪条分支，第 5 层永远是第 5 层这个高度。 |
| **swipe 组** | 同一楼层上的一份内容。**该层 swipe 组数 > 1 = 该层就是分叉点。** |
| **swipe** | 宿主原生左右箭头所切的东西——同一条消息的多次生成变体。它只改变**这一层显示什么内容**，不改变分支。 |
| **分支** | 从某个楼层分出去的一条路。它记的是「这一层用哪个组、下一层用哪个组」这样的**引用序列**，**不复制内容**。 |

> 术语提示：早期文档里把这个叫「变体」，本仓现在统一叫 **swipe**。

### 存法（为什么分支很省空间）

- 每条消息正文单独存放，坐标是「**哪个家族、第几层、第几个 swipe 组**」。
- 分支**不存正文**，只存一份引用表：这条分支在第几层选了哪个组。
- 同一段历史被多条分支共用时，库里**只有一份**，不是每条分支各存一份。
- 所以：一个家族只占**一份**历史正文的量；分出十条分支，正文还是这一个家族的量。
- 为什么可以只存引用：分支之间的差别只在**分叉点之后**；分叉点之前每层几条分支指的是同一批内容。
  引用表把「共享」直接记进数据结构，共享部分天然只有一份，**不需要事后去重**。

### 三种模式

| 模式 | 内容存在哪 | 磁盘上还有聊天文件吗 |
| --- | --- | --- |
| **JSONL 增强** | 聊天文件（和没装插件时一样） | 有，酒馆自己维护 |
| **纯数据库** | 只存库 | 没有 |
| **双写** | 库（**库是准的**） | 有，插件按 **1.5 秒**的节奏把库里的当前分支写一份标准文件出来 |

**双写**是为了「既要库的好处，又不想失去一个能直接打开、能备份的文件」。
它**只写不读**：读和写一律走库，磁盘那份文件的改动**不会被采纳回库**
（把文件收进库是「导入」的活）。

### 切模式时的安全动作

| 切换 | 插件会做什么 |
| --- | --- |
| 库模式 → JSONL 增强 | 先把当前分支写成文件；**写失败就不切** |
| 纯数据库 → 双写 | 立刻写一次 |
| 双写 → 纯数据库 | 停止写文件；磁盘上那份留着当快照 |

## 边界与未做到

- **双写不是备份方案**：它是**滞后快照**（约 1.5 秒节流），且**只写不读**。
  按磁盘那份文件去改，改动不会回到库里——会形成静默的数据分叉。
- **双写与保密目标冲突**：只要磁盘上还留着明文 jsonl，「库内加密」就失去意义。
  这一点在[隐私边界](/guide/privacy)里如实写明。
- **纯数据库模式下没有聊天文件**：宿主与依赖聊天文件的第三方工具会看不到这些聊天。
- 跨三模式的**行为一致性回归**与**多插件共存实测**尚未完成（见[路线图](/dev/roadmap)）。

## 失败与降级时的表现

- 切到「库模式」前的那次文件写入**失败即中止切换**——不会出现「切了但文件没落地」的中间态。
- 双写落盘失败**只记状态、不阻断聊天**（聊天照常走库）；盘上那份可能落后，属预期行为。
- 存储后端不可用时沿降级链回退，**不阻断使用**（见[三档存储与降级](/guide/storage-tiers)）。

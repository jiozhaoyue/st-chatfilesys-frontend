## 一、这个数据库怎么存聊天

### 四个概念，各一句话

- **聊天家族**：一个角色名下互为分支的一批聊天，合成一个家族。从前它们是磁盘上互不相干的一堆文件；现在它们是同一个家族里的不同分支。
- **楼层**：一条消息占一个楼层位，家族内统一编号。不管走哪条分支，第 5 层永远是第 5 层这个高度。
- **变体**：同一个楼层上可以有几个不同的内容版本，也就是酒馆原生的「滑动」。变体只影响这一层显示什么内容，不改变分支。
- **分支**：从某个楼层分出去的一条分支。它记的是「这一层用哪个变体、下一层用哪个变体」这样的引用序列，不复制内容。

### 存法

- 每条消息正文单独存放，坐标是「哪个家族、第几层、第几个变体」。
- 分支不存正文，只存一份引用表：这条分支在第几层选了哪个变体。
- 同一段历史被多条分支共用时，库里只有一份，不是每条分支各存一份。
- 所以一个家族只占一份历史正文的量。分出去十条分支，正文还是这一个家族的量。
- 磁盘上的聊天文件是不是常驻物，按你选的模式定（见下）。

### 为什么可以只存引用

分支之间的差别只在分叉点之后。分叉点之前的每一层，几条分支指的是同一批内容。引用表把「共享」这件事直接记在了数据结构里，所以共享部分天然只有一份，不需要靠去重算法事后合并。

### 三种模式（弹窗的「设置」页签里三选一）

| 模式 | 内容存在哪 | 磁盘上还有聊天文件吗 |
|---|---|---|
| JSONL 增强 | 聊天文件（和没装插件时一样） | 有，酒馆自己维护 |
| 纯数据库 | 只存库 | 没有 |
| 双写 | 库（库是准的） | 有，插件按 1.5 秒的节奏把库里的当前分支写一份标准文件出来 |

双写是为了「既要库的好处，又不想失去一个能直接打开、能备份的文件」。它只写不读：读和写一律走库，磁盘那份文件改动不会被采纳回库（把文件收进库是「导入」的活）。

切模式的安全动作：从库模式切回 JSONL 增强之前，插件会先把当前分支写成文件，写失败就不切；从纯数据库切到双写会立刻写一次；从双写切回纯数据库则停止写文件，磁盘上那份留着当快照。

## 二、怎么接管

### 接管的位置

酒馆所有聊天读写最后都走同一个网络出口：读聊天、存聊天、追加消息、打补丁、改名、删除，都是向这个出口发请求。插件在这个出口上装了一层拦截层。

拦截层对每个请求做一次判断：

- 属于插件已经在管的家族 → 插件自己应答，不发给服务器。
- 不属于 → 原样发给服务器，跟没装插件时完全一样。

### 读聊天这条路

酒馆要打开一个聊天时，拦截层从库里按坐标取出「当前这条分支引用的那些楼层」，按酒馆期待的格式组装成一份完整回复交回去。

酒馆拿到的东西和它平时从服务器拿到的形态完全一样，所以它的画面渲染、翻页、滚动、消息操作，以及其他插件对这些消息的读取，全都照常工作。插件不需要改酒馆的任何一行代码。

### 存聊天这条路

酒馆发出存聊天请求时，里面带的是整份聊天内容。拦截层把它拆回「第几层、第几个变体」，写进库，然后回一个「已保存」的答复。酒馆不需要知道内容去了哪。

写的时候带一个版本号做比对：如果拿到的版本号说明「你手上的内容已经过期」，插件会回一个明确的冲突答复，酒馆按它自己的规矩重新拉一次再写。这样两处同时改同一个聊天时不会互相覆盖。

### 为什么其他东西不受影响

- **其他插件的请求**：拦截层只认聊天那一族请求，别的请求原样转发，头部和参数一个不改。
- **其他插件自己的数据**：酒馆有一类数据是「跟某个聊天绑定的插件状态」，那是别人存放自己东西的地方。插件对它只做转发，不读不写。这是有意的：纯数据库模式不该顺手接管别人的状态。
- **未在本插件管辖的聊天**：一律原样放行。插件不是把整个酒馆的聊天都抢过来，只接管它已经建立的家族。
- **出错时**：任何一步异常，拦截层都退回原生请求，只留一条控制台警告，绝不阻断酒馆。插件坏了不影响你正常聊天。

## 三、怎么接管「创建分支」和「创建检查点」

### 酒馆原本这两个功能做什么

按官方文档的说法，两个功能都是**把当前聊天复制一份**，区别只在三个地方：

| | 创建分支 | 创建检查点 |
|---|---|---|
| 复制范围 | 从开头到你所点的那一层 | 从开头到你所点的那一层 |
| 名字怎么来 | 自动生成，用户不能改 | 弹窗让用户起名，留空则自动生成 |
| 建完是否切过去 | 立刻切到这份新聊天 | 不切，留在原地 |
| 消息上留什么 | 不留可见标记（记在消息的附加信息里，可以有多条） | 留一个旗标，点旗标跳过去；一条消息上只能有一个，再建会替换旧的那个 |

两者的共同点是最要紧的：**都是复制一整份聊天**。这是聊天文件越来越大的直接来源——同一个角色分三次支，磁盘上就有四份几乎相同的历史。

### 设计上应该变成什么样

- 点「创建分支」：不再复制。在当前家族里，按当前这一层记下一条新的分支（引用已有的历史），然后切过去。家族体积不增加，磁盘上不产生新文件。
- 点「创建检查点」：同样不再复制。记下一条新的分支，名字用用户输入的那个，**不**切过去，同时在那一层保留旗标。点旗标跳过去，就等于切到那条分支。
- 两者在数据上是同一件事的两种用法——都是「从某一层分出去的一条分支」。差别只剩三点：名字从哪来、建完切不切、消息上留不留旗标。

### 现状

**这两条路已经接管了（代码完成，真机用例在跑）。**

插件在「新聊天被建立之前」拦住它：认得出「这是一份从某个家族分叉出来的内容」，于是直接在库里记下这条新分支并回一个成功答复，磁盘上不会出现那份复制文件，也不会把这个新名字当成一个新家族。

认的方式有三重，任何一重不成立就原样放行（宁可不接管，也不吞错）：

1. 酒馆写的这份内容里带着「我是从哪个聊天分出来的」这条线索，而这个聊天在库里能找到；
2. 正文内容必须正好是那个聊天当前分支的**前一段**（同样长度或更短，逐行相同）；
3. 名字：分支名是酒馆自动生成的、用户改不了，所以名字里带「- Branch #序号」的就是分支；剩下的都当检查点（检查点的名字用户可以自己起，所以不能靠名字认）。

接管之后，分支和检查点在库里是同一种东西（都是「从某一层分出去的一条分支」），差别只剩三点——名字从哪来、建完切不切过去、消息上留不留旗标。

具体到你自己能看到的：

- 点「创建分支」：库里多一条分支，酒馆切过去，你看到的是到那一层为止的内容；点左侧菜单的「返回父聊天」能回到原来那个聊天，看到完整内容。
- 点「创建检查点」：库里多一条分支，名字就是你输入的那个，酒馆**不**切过去；原消息上留下旗标，点旗标跳进去看到的是「到那一层为止」的内容。

## 四、具体是什么效果

### 你能感觉到的变化

- **体积**：一个角色只有一份历史正文。分出去多少条分支都不翻倍。
- **打开**：聊天不再需要一次性读完整个文件再解析，按层取用。超大聊天打开时不再卡在读文件上。
- **切换分支**：只改「现在走哪条引用序列」，不换文件、不发请求，切换是即时的。
- **导出**：磁盘上的聊天文件只在导出时生成。导出一条分支 = 一份标准聊天文件，原生酒馆可直接打开；导出整个家族 = 每条分支一份，打包成一个压缩包。
- **导入**：安装后可以把已有的聊天文件录入数据库。录入时会做内容比对：两边完全相同的楼层只留一份，从相同前缀之后分出去的部分各记成一条分支。这样多个文件之间的重复历史会被消掉。
- **删除安全**：录入完成后，源文件不是直接删除，而是先移进插件管理的回收站，默认保留七天，期间可以还原。是否删除在动手前会问你，默认建议删。
- **出问题的兜底**：任何一步出错，插件退回酒馆原生行为，只留控制台警告。不会让你没法聊天。

### 刻意不变的部分

这几条是「接管铁律」，属于绝对确保项：

- 聊天的画面、消息操作、滑动、编辑、删除、重新生成——不变。
- 酒馆自己的按钮照旧可点、行为照旧——不变。
- 其他插件产生的按钮照旧可用，其他插件自己的数据插件不碰——不变。
- 导出的聊天仍是标准格式，脱离插件也能打开——不变。
- 必要的时候插件会把自己伪装成「磁盘上还是有聊天文件」的样子，让依赖这个前提的逻辑继续正常工作——这是刻意的。

## 五、界面长在哪里

插件只有一个界面：**弹窗**。扩展设置里不放任何东西，聊天界面上也不放别的。

**入口**：输入框上方那排工具图标里的一个插件按钮（和酒馆自己的图标同一排、同一风格），或者快捷键 Alt+B。以前有过斜杠命令 `/cb`，已经删掉。

**弹窗里四个页签**：

- **当前聊天**：结构树（只画结构：分支编号、分支名、层数，不含消息内容）；分支管理（改名、删除分支、AI 总结）；本聊天的库操作（转库、导出当前分支、与库同步一次）。
- **角色卡的聊天**：列出这个角色名下的聊天，可以逐个转数据库、导出、看它的结构树。
- **设置**：存储模式三选一（JSONL 增强 / 纯数据库 / 双写）、保存后自动导出、当前存储档位提示。
- **回收站**：列出、还原、立刻清理。

弹窗里不会逐条列出楼层。以前有过一个「楼层」页签，按楼层号一行一行列出消息，已经删掉，不再出现。

**聊天界面只有两样**：

- 上面说的那个入口按钮。
- 消息旁的一个**版本按钮**，只在这一层有多个 swipe 组（也就是这一层是分叉点）时才出现。它显示的是「当前是第几组 / 一共几组」，形状是分叉图标加计数，不用左右箭头——箭头那个形状是酒馆原生滑动自己的。

点这个按钮会打开一个窗口，列出这一层的全部版本（每个组有几个版本都列出来），并且：

- 能只看不改地预览某一版正文，当前在用的那一版有标记；
- 能切过去。切换**同一组内**的版本只换这一层的内容，后面的楼层不受影响；切换**别的组**的版本等于换到那条分支；
- 能勾选删除多余的版本（至少留一个），删掉正在用的那一版就自动接管下一版，最后一版则接管前一版；删除是一版一版按从后往前的顺序做的，每次都会通知酒馆一次，这样别的插件记的下标不会错位；
- 能调整顺序、也能直接改某一版的正文。

属于别的组的版本只能预览和切过去，不能在这里删除或改写——那些内容归另一条分支，要动它们请走分支管理。

除此之外，聊天界面里没有插件加的任何东西：没有徽章、没有每条消息旁的分叉按钮、没有分叉点记号、没有工具条、没有悬浮窗。

**新增分支走酒馆自己的入口**：酒馆原生的「创建分支」「创建检查点」按钮，背后由本插件接管（写进库里，不在磁盘上产生复制文件）。插件自己不提供任何新建按钮。
